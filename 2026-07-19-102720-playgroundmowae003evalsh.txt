❯ playground/mowa_e003_eval.sh测试脚本是不是可以多进程                          

  Thought for 18s, read 3 files (ctrl+o to expand)

● playground/mowa_e003_eval.sh 现在是单进程顺序执行的：启动一个 policy server →
  依次对每个 task 启动一个 client → 一个 task 跑完再跑下一个。不过底层链路已经具
  备了做多进程/并行的基础，只是脚本没有利用起来。

  当前脚本的多进程潜力

  1. 单 server 可服务多 client
  deployment/model_server/server_policy.py 里的 WebsocketPolicyServer
  监听一个端口，多个 client 可以同时连上来请求推理。
  2. simulation_env.py 已经支持多 env 并发
  examples/Robocasa_365/eval_files/simulation_env.py:121 的 run_simulation
  会根据 n_envs 选择：
    - n_envs == 1：SyncVectorEnv
    - n_envs > 1：AsyncVectorEnv(..., context="spawn")
  所以只要把 --args.n-envs 改大，就能在一个 client 里并发跑多个 robocasa
  环境。但注意当前脚本里写死了 --args.n-envs 
  1（playground/mowa_e003_eval.sh:191）。
  3. 多 task 也可以并行
  因为 server 是无状态的（每个请求独立图像+语言指令），你可以同时启动多个
  simulation_env.py 实例，各自评估不同 task，共享同一个 server。

  如果你想改成多进程，最常见的改法

  方案 A：单个 client 内多 env（最简单）

  把脚本里的 --args.n-envs 1 改成 --args.n-envs 4 之类的值，同时确保 N_EPISODES
  能被 n_envs 整除或处理好余数。

  局限：所有 env 共享一个 client 进程，GPU 侧仍然是串行处理每个 obs；适合 CPU
  侧环境模拟慢、GPU 推理快的场景。

  方案 B：多 task 并行（server 共享，client 并发）

  保持 server 单实例，但把 for env_name in ... 循环改成后台并行，例如用 GNU
  parallel 或 & + wait。每个 task 有自己的 client log 和 result json。RESUME
  逻辑仍然有效，因为结果文件是按 task 分开的。

  这种方式的好处是 GPU 利用率更高：一个 task 的 env 在等 CPU 模拟时，另一个 task
  的 client 可以发请求给 server。

  方案 C：每个 GPU 一个 server + 多 task 分片

  如果有多张 GPU，可以按 task 分片：
  - GPU 0 跑 task 1/2/3
  - GPU 1 跑 task 4/5/6

  每个分片独立跑一份 mowa_e003_eval.sh，指定不同的 GPU 和 PORT 即可。

  ---
  需要我直接帮你把 playground/mowa_e003_eval.sh 改成**方案 B（多 task
  并行）或者方案 A（单 client 多 env）**吗？

  实际调用频率

  client 找 server 推理一次，大约每 n_action_steps 个 env step（默认是 8 个 env
  step），不是 256。

  流程是：

  1. run_simulation 主循环一次调用 model.step(obs)。
  2. PolicyWarper.step() 把 server 返回的 action_chunk_size=32 的 action chunk
  切成前 n_action_steps=8 步：
  raw_actions[:, : self.n_action_steps, s:e]
  3. 这个 (B, 8, D) 的动作交给 MultiStepWrapper.step()。
  4. MultiStepWrapper 在内部执行 8 次 env step（把 8 个动作依次喂给 base env）。
  5. 8 步跑完后，主循环再次调用 model.step(obs)，重新请求 server。

  所以 server 每次返回 32 个动作，但当前代码只取了前 8 个，剩下 24
  个被浪费了。client 大约每 8 个 env step 就找 server 一次。

  为什么 GPU 还是 0%

  如果模型正常在 GPU 上，应该每隔 8 个 env step 出现一次短暂的 GPU
  尖峰。你观察到长时间为 0，可能的原因：

  尖峰很短，容易被 nvidia-smi 采样错过。
  3. 模型卡在第一次推理，根本没返回（比如显存分配 hang 住）。

● 对，robocasa 和 libero 的评测循环本身就不一样，所以 GPU
  利用率的表现不同是正常的。

  核心区别

  1. 调用 server 的频率不同

  LIBERO 的 ModelClient 有一个 action chunk cache：server 一次返回 32
  个动作，client 把 32 个动作按顺序用掉，每 32 个 env step 才找 server
  一次。但因为 LIBERO 的 env step 很快，32 步很快就跑完，server
  很快就会收到下一个请求，所以 GPU 看起来“一直在忙”。

  RoboCasa 这边：
  - MultiStepWrapper 一次只执行 n_action_steps=8 个 env step，然后才调用一次
  model.step()。
  - 目前 PolicyWarper.step() 每次只取 server 返回的 32 个动作中的前 8 个，剩下的
  24 个直接浪费了。
  - 更关键的是，robocasa 的 env step 本身很慢（MuJoCo 物理 + 双视角渲染），8 个
  env step 可能要跑好几秒，server 在这段期间完全闲着。

  所以不是 GPU 没工作，而是 GPU 工作一会儿、歇一会儿，nvidia-smi
  的平均利用率就显示为 0。我们实测能看到 90%+ 的尖峰：

  09:57:12 98 18199

  2. 环境渲染开销不同

  LIBERO 的 OffScreenRenderEnv 相对轻量；robocasa 每个 env step 都要渲染
  agentview_left 和 eye_in_hand 两个相机，并且视频录制还要再拼接/编码，单个 env
  step 耗时明显更长。

  3. 模型类型不同

  - LIBERO 用的是 QwenOFT/FAST 这类自回归/并行动作头，单次推理相对快。
  - MoWA-E-003 是 Wan2.2 流匹配扩散模型，一次推理要跑 4 步扩散，单次 2~3
  秒，但调用次数更少。

  结论

  Robocasa 这边 GPU 利用率低不是因为代码没上 GPU，而是因为：

  ▎ server 推理只占一小部分时间，大部分时间花在 MuJoCo 环境模拟和双视角渲染上。

  如果想让 GPU 看起来更“满”，有两个方向：

  1. 在 PolicyWarper 里也实现 action chunk cache（像 LIBERO 那样把 32
  个动作用完），能把 server 调用次数降到原来的 1/4，但 env
  模拟本身是瓶颈，总时间提升有限。
  2. 同时跑多个 task 共用一个 server，server 可以把不同 task 的请求 batch
  起来，GPU 利用率会更高。

  需要我实现第 1 点（复用 action chunk）吗？它不会显著缩短总时间，但会让 server
  端 GPU 利用率更连续。
